# SkillSense AI

Skill assessment, resume analysis, placement intelligence and coding practice for students; admin tools for papers/questions/placements.

## Stack
- Frontend: React 18 + Vite (JS, no TypeScript), react-router-dom v6, framer-motion, three.js/R3F
- Backend: FastAPI + MongoDB via `motor`; JWT (python-jose), bcrypt, slowapi rate limiting
- "AI" is rule-based scoring + TF-IDF similarity (scikit-learn). No LLM calls.

## Folder map
- `src/pages`, `src/pages/admin` - route pages; `src/components` - shared UI
- `src/services/*Service.js` - API clients (all go through `src/services/api.js`)
- `src/context` - Auth/Notification contexts; `src/utils/normalizers.js` - API response shaping
- `backend/app/main.py` - app, CORS, routers; `config.py` - settings (fails fast on bad secrets)
- `backend/app/routers` - HTTP layer; `services` - business logic; `models` - pydantic
- `backend/app/repositories` - Mongo access (P2); `data` - seed data & static config
- `backend/tests` - pytest; `backend/.env` is local only (git-ignored)

## Run
Backend (from `backend/`):
```
python -m venv .venv && .venv\Scripts\activate    # source .venv/bin/activate on mac/linux
pip install -r requirements.txt
copy .env.example .env   # then set JWT_SECRET_KEY
uvicorn app.main:app --reload --port 8000
```
Frontend (repo root): `npm install && npm run dev` (needs `VITE_API_BASE_URL`, see `.env.example`).
Data: MongoDB is required. Load starter content with `python -m app.seed` (idempotent). With no Mongo in local dev only, set `ENABLE_MEMORY_FALLBACK=true` (throwaway mongomock DB, auto-seeded, responses carry `X-Data-Store: in-memory-fallback`).
Launch on Windows: `run_skillsense.bat` or `npm run backend` (both use `backend\.venv`, never `backend\python_bin`, which lacks dependencies and makes the Vite proxy answer 500 on every `/api` call). `npm run backend:check` prints one `STARTUP CHECK OK/FAILED` line (packages, `.env`, Atlas).
Auth proof in real Chrome: `npx playwright test -c e2e/playwright.config.js auth-fix`.
Checks: `npm run build`, `pytest backend/tests`.

## Rules
- NEVER read or grep `node_modules`, `dist`, `backend/python_bin`, `backend/.venv`, `package-lock.json`.
- No silent `except: pass` around database calls; DB failures surface as HTTP 503.
- No hard-coded demo metrics or fallback mock data: every number shown comes from stored data (new user = zeros).
- All protected routes use `require_student` or `require_admin`; never trust a client-sent role.
- No secrets, default passwords or demo credentials in source. Demo accounts only when `ENV=development` and `ENABLE_DEMO_ACCOUNTS=true`, passwords from env.
- Keep URLs and response shapes stable unless the task says otherwise; frontend depends on them.
- Never print or log secrets (passwords, tokens, API keys, connection strings, SMTP app passwords). Log the error type, not the payload.
- Keep API response shapes stable; add fields, don't rename or remove them.
- Ask before deleting any file or folder.
- Run the tests (`pytest backend/tests`, `npm run build`) after each change.
- Code execution: the default is `SANDBOX_MODE=online` (set `CODE_PROVIDER` in `backend/.env`; default `judge0_ce`, the free public Judge0 CE instance). No Docker and no local compilers are needed, but it requires internet. The provider URL and any API key (`CODE_API_URL`, `CODE_API_KEY`) live only in the backend; the browser only calls our own `/practice/code/run` and `/submit`. Only source code, language and stdin are sent to the provider. A slow, down or rate-limited provider returns 503/429 with a friendly message, never a fake success or a Wrong Answer. `subprocess` (local, dev only, not a security boundary) and `docker` (real isolation) stay in the code as alternatives; tests never call the internet (mock the provider).
- Coding problems: 12 original stdin/stdout problems in `backend/app/data/coding_problems.py` (4 easy, 5 medium, 3 hard; classic read-input/print-output, no per-language wrappers). Each has 2 shown samples + 2-3 hidden cases (judge runs 5 max, stops at the first failure) and starter code in all five languages (Java is `public class Main`). `python -m app.seed` upserts them (keeps `edited_by_admin`) and removes `RETIRED_PROBLEM_SLUGS`. The API never returns hidden cases (`_public` in `routers/practice.py`); a wrong answer shows input/expected only for a shown case. Verdicts: Accepted, Wrong Answer, Runtime Error, Time Limit Exceeded, Compile Error, and `Judge unavailable` when the provider fails (never Wrong Answer, and no attempt is saved). Attempts store `verdict` + `runtime_ms`; `GET /practice/solved` drives the solved badge. To add a problem: add it to the data file, add a reference solution to `backend/scripts/reference_solutions.py`, then run `python scripts/check_reference_solutions.py [--starters]` from `backend/` (real provider, needs internet, not part of pytest). Frontend uses API data only; `src/data/mockCodingProblems.js` is unused.
- P4 browser proof: `npx playwright test -c e2e/playwright.config.js p4-judge` (headed Chrome, real Judge0, screenshots in `e2e/screenshots/p4/`, deletes its test student).
- Resume analyzer: `routers/resume.py` (`/resume/analyze` file, `/analyze-text` edited text, `/history` last 10), `services/resume_extract.py` (magic-byte validation, PDF/DOCX/TXT/image reading, OCR), `services/resume_service.py` (sections, evidence, ATS-style score), `data/skills.py` (catalog). Files: PDF/DOCX/TXT/PNG/JPG/WEBP, 8 MB, first 4 PDF pages; the raw file only touches a temp file deleted in `finally`, and only scores, skills and a text hash are stored. OCR: `OCR_ENGINE=rapidocr` (pip `rapidocr-onnxruntime`, default) or `tesseract` (needs the program); the other is tried if one fails to load, and with neither, only scans/photos return 503 "OCR engine unavailable". Use only pip packages here (Windows Application Control blocks some DLLs) and test each import in `backend\.venv`. OCR drops spaces, so `restore_spaces` (wordninja + skill terms) runs on OCR text. Ambiguous skill aliases (c, r, go, os, ml, dl, rest, node, spring, py) count only in a Skills section or with context; add new skills in `data/skills.py` and map new career_config labels in `REQUIREMENT_MAP` (a test fails on any unmapped label). The score is labelled "ATS-style score (estimate)": nine rule-based categories summing to 100, never a real ATS result. Unknown `career_path` is 400, never a default role. Fixtures: `backend/tests/fixtures/make_fixtures.py`. Browser proof: `npx playwright test -c e2e/playwright.config.js p5-resume`.
- Courses: 13 courses in `backend/app/data/courses.py` (seeded by `python -m app.seed`, `edited_by_admin` respected). Skills use the canonical names from `data/skills.py` (a test enforces it). Resources are ONLY a provider name plus its official home page, never a deep link (a test checks the URL shape); each is marked `verify link`. Endpoints: `GET /courses` (skill, level), `GET /courses/{slug}`, `POST /courses/{slug}/progress`, `GET /student/courses`; progress is per student in `course_progress`; finishing a course creates a notification.
- Recommendations: `services/recommendation_service.py`, `GET /recommendations/courses`. Score: +3 per unmet required skill of the career path (credited to ONE course, the first alternative that has one), +2 per assessment gap, +1 per weak topic, +2 per skill missing in the latest resume analysis; completed courses never appear; no data = beginner courses with reason "Start here"; 4-week plan of about 8 h/week. Shown on Dashboard, Roadmap and under the resume fixes (`course_slug` on each fix). P5's generic "Learn <skill>" only remains when no course covers the skill.
- Question bank: authored questions live in `data/questions_*.py` (built with `data/qhelp.q`, options shuffled by a seed from the id, so answer positions never change) and are joined in `data/assessment_extras.py`. Fields: id, skill, topic, difficulty, question_type (Conceptual, Code Output, Find the Error, Scenario), question_text, `code`, options (exactly 4), correct_option_index, explanation, origin "authored", practice, companies. NEVER send `correct_option_index` (non-null) or `explanation` before submit: only `repositories/assessment_bank.scoring_data` and the verify/answer endpoints read the key (a test scans every question payload). Never copy questions from websites or books. Company tags (TCS, Infosys, Wipro, Accenture, Cognizant, Capgemini, Amazon) are shown as "Pattern-inspired practice" (`QuestionBody`), never as real past questions; only a question from an admin-uploaded paper is a previous-year question. After editing questions run `python scripts/validate_questions.py [--online]` from `backend/` (it runs every Python/JavaScript Code Output snippet with a 5 s timeout, and `--online` compiles and runs the C, C++ and Java ones; fails loudly). It must pass, and `pytest` runs the same checks.
- Resume practice: `GET /resume/questions?analysis_id=&company=` builds a personal set from one stored analysis (claimed or missing skills start Easy, shown skills Medium, verified Hard) plus interview prompts from templates that name only skills (and projects) found in that resume, labelled "generated template". Each analysis has an `id`; a student can only open their own.
- Notifications come from `GET /notifications` (empty until something real happens, such as finishing a course). Nothing in the UI is hard-coded. Previous questions that linked to a retired practice problem are relinked to the closest current problem, or to no link, by the seed.

Above 768px: only the fixed 264px sidebar (`.app-sidebar`) and content with `margin-left: 264px`; the mobile header is not rendered at all. At 768px and below: a fixed top bar (`MobileSidebarChrome`), off-canvas sidebar with a backdrop that closes on backdrop click, Escape and route change, content with no left margin. Use the `useMobileSidebar` hook; never add another chrome breakpoint (content grids may still reflow fluidly).
- UI audit: `npm run test:ui` (headless Chrome; login, register, student dashboard, practice, resume analyzer, assessments and the admin dashboard at 1280/768/390px; screenshots + `report.md` in `e2e/screenshots/ui/`). It fails on horizontal scroll, console errors, a visible mobile header above 768px, or a broken/clipped sidebar or drawer. `UI_WIDTHS=390,1280` runs a subset; add routes to the lists at the top of `e2e/ui-audit.spec.js`. Needs the backend (8000) and `npm run dev` (5173) running, or Playwright starts them. Admin pages use `ADMIN_TEST_EMAIL`/`ADMIN_TEST_PASSWORD` when set, otherwise a stubbed session (layout checks only).
- Readiness: `services/readiness_service.py` is the only place it is calculated, from the student's own records, never stored (the old stored `users.readiness_score` is not written or read any more): 40% average of the latest score per assessment, 20% coding accuracy (problems with an Accepted submission / problems attempted; snapshots are not attempts), 15% learning (mean of the roadmap % and the progress in started courses, only the parts that have data; 0% done counts as no data), 15% latest ATS-style resume score, 10% consistency (active days in the last 14). No data for a part = 0 for that part. `compute()` is pure (tested with known data); `load_raw`/`readiness_for_users` batch the queries for admin lists. Streak = consecutive days with an assessment or a coding/practice attempt. `/student/dashboard`, `/student/progress`, `/practice/stats`, `/admin/students` and `/admin/analytics` all use it. Career-path `match_percentage` is computed per student from their skills (0 for guests), never stored in `career_config.py`.
- Reports and exports: `GET /student/report.pdf` (reportlab, `services/report_service.py`; a new student gets a valid report that says nothing is recorded) and `GET /admin/students/export.csv` (admin only; `csv_cell` prefixes any text cell starting with = + - @ tab or CR with an apostrophe so a name cannot run as a formula). The browser downloads both through `api.download` / `utils/download.js`.
- Every page that loads data shows `LoadingState` while loading, `EmptyState` when there is nothing, and `ErrorBanner` (with Try again) when the request fails. Services must throw on failure (never `return []` from a catch), so the page can show the banner. No page or service imports `src/data/mock*.js` (the remaining mock files are unused). Company stats: `GET /question-intelligence/summary` returns `empty: true` when no previous questions are published.
- P7b browser proof: `npx playwright test -c e2e/playwright.config.js p7b-dashboard` (headed Chrome; new student zeros, numbers after real activity match the API, report PDF download; admin steps run only when `ADMIN_TEST_EMAIL` and `ADMIN_TEST_PASSWORD` are set; screenshots in `e2e/screenshots/p7b/`).
- Assessment sessions (P8): `POST /assessments/{id}/start` (student only) creates or reopens (same questions, saved answers, same deadline) an `assessment_sessions` document: session_id, user_id, assessment_id, question_ids in shuffled order, started_at, expires_at = start + the set's duration; the response has NO answer keys and `seconds_remaining` for the countdown. `PUT /assessments/sessions/{id}/answers` autosaves. `POST /assessments/{id}/submit` (or `/submit`) REQUIRES `session_id`: only that session's questions are scored; another student's or an unknown session is 404, an expired one (30 s grace) is 410, a second submit is 409 (atomic `mark_submitted`, released again if storing the attempt fails). `GET /assessments/{id}` returns details with an empty `questions` list (questions only come from start) and needs login. The submit response and `GET /assessments/result/latest` carry `review` (every question, your answer, the correct answer, the explanation: the only place keys appear), `topic_scores[].band`, `gap_topics` and `next_steps` (real course / set / roadmap links). `result/latest` is 404 when nothing was taken (no baseline). Bands (`band_for`): under 60 gap, 60-79 developing, 80+ strong; gap topics are stored on the attempt and on the user (`users.gap_topics` = newest result per topic). `/assessments/practice/*` and `/practice/questions*` need login and only serve `practice=true` questions (graded-only ones are 404 / absent); tests use `take_assessment` in `tests/conftest.py`.
- Roadmap (P8): `services/roadmap_service.build_roadmap` is pure. Status = the saved status or `not_started`; `locked` is computed (never saved, PUT with it is 422): a milestone is open when it is the first, the previous one is completed, or an assessment set of its linked course was passed with 70%+. A locked milestone cannot be started (409). `is_priority_gap` = a gap topic matches the milestone's skills/title (`matches_gaps`); the list is ordered completed, in progress, not started (priority first), locked. `courses`/`course_slugs`/`practice_sets` come only from the real `courses` and `assessments` collections (`courses_for`; a language course is only offered when the milestone or the career path names that language). `score` is the best score on a related assessment, never the seeded number. Progress is stored per (user, career path title); PUT checks the milestone belongs to the student's current path (404). The roadmap page saves the chosen track with `POST /student/career-path`.
- P8 browser proof: `npx playwright test -c e2e/playwright.config.js p8-sessions` (headed Chrome, real Atlas; refresh mid-test, review and bands, roadmap markers, API double submit = 409, auto-submit, expired message; `e2e/helpers/move_session_deadline.py` moves a test student's deadline; screenshots in `e2e/screenshots/p8/`; the test student is deleted).
- Admin question papers (P9): `POST /admin/question-papers/upload` reads the file with `services/resume_extract.extract_resume` (magic-byte check, 8 MB, OCR for scans/photos, temp file deleted; `.json` papers are parsed directly). EVERY extracted question starts `needs_review`; low OCR confidence (<60) also sets `low_confidence`. `PUT /admin/extracted-questions/{id}/status` takes a JSON body `{"new_status": needs_review|approved|published|rejected}` (anything else is 422; same for `PATCH /placements/{id}/status` with draft|published|closed). Approve/publish records `approved_by` and `approved_at`, copies the question into `previous_questions` with status `published` and notifies students targeting that company (once per paper); any other status removes that copy. The TF-IDF match index is built ONLY from `previous_questions` with status `published` (`repositories/questions.published_previous`) and is rebuilt after every approve/publish/reject/delete. `extracted-questions`, `question-papers/{id}/questions` and `previous-questions` take `page` and `page_size` (max 100, else 422) and return the total in `X-Total-Count`; `extracted-questions` also takes `status`. The sklearn pin in `requirements.txt` stays at 1.9.0.
- Placement eligibility (P9): `services/placement_service.py`. A student sees skill match only when they have assessed skills (`match_known`); eligibility uses the optional profile fields `cgpa` (0-10), `branch`, `graduation_year` (2000-2040) against the job's `minimum_cgpa`, `eligible_branches`, `graduation_year`: `unknown` says "Add CGPA to see eligibility" (or what else is missing), `not_eligible` lists the reasons, a job with no criteria says "No eligibility criteria listed". `/docs`, `/redoc` and `/openapi.json` are off when `ENV=production`; CORS allows `FRONTEND_URL` only (plus the localhost dev origins outside production). Every `/api/admin/*` route (and placement writes) is `require_admin`: 401 anonymous, 403 student (a test walks the OpenAPI schema).
- Admin content editor (P9): `routers/admin_content.py` (`/admin/content/questions|courses|career-paths`, `/meta`), rules in `services/content_validation.py` (shared with `scripts/validate_questions.py`). A problem is a 422 `{detail: {message, errors: [...]}}`; the api client keeps it as `error.detail`. Create/edit/deactivate (no hard delete); everything touched gets `edited_by_admin: true`, so `python -m app.seed` skips it. A deactivated question leaves practice, resume practice and NEW assessment sessions (running sessions keep their questions); a deactivated course leaves the catalogue and recommendations (progress is kept). Course slugs and question ids cannot change; renaming a career path migrates saved roadmap progress and student records that use its title. Page: `/admin/content`.
- Notifications (P9): collection `notifications` (id, user_id, type, title, message + body, link, read, created_at, optional `dedupe_key`); `services/notification_service.py` creates them (`notify`, repeat events carry a dedupe key so nobody is told twice) for: assessment completed, new recommended course after a resume scan (each course once), a paper approved for a target company, a new published placement that matches the student's skills (>=50% of required skills and not ruled out), and a placement deadline within 3 days. The deadline check runs from `services/scheduler.daily_loop` (started in the app lifespan except when ENV=test; wakes hourly; `repositories/jobs.claim_day` stores `last_run_date` in `job_runs`, so it runs once a day across restarts; a failure releases the day, is logged by type and never stops the app). Email copies (placement matches and deadlines only) go through `email_service` and ONLY if `users.email_notifications` is true (default false, set in Settings via `PUT /student/settings`) AND the email is verified; each has a signed one-click unsubscribe link (`/unsubscribe?token=` page -> `POST /notifications/unsubscribe`, no login, works once per student through `users.unsub_version`, tampered/expired/used tokens are 400). With `EMAIL_ENABLED=false` only the message type is logged (and the link in development); bodies and passwords are never logged.

Proof with open lists at 1280px and 390px: `npx playwright test -c e2e/playwright.config.js p7-dropdowns` (output in `e2e/screenshots/p7/`).
